Mais comment on s’en sert ?

1er probléme

Le contexte est limité


  • Un agent n’a pas automatiquement toute la connaissance du projet
  • Une conversation peut être interrompue ou remplacée
  • Un long historique peut devenir coûteux et difficile à exploiter
  • Une information importante peut être oubliée ou mal interprétée

il nous faut donc une zone mémoire

où doit vivre la connaissance.



Dans le dépôt, autant que possible.

Et pas uniquement dans une conversation.

2ème problème

L’agent a besoin d’une méthode stable


  • Il peut adopter des approches différentes d’une conversation à l’autre
  • Il ne connaît pas forcément nos conventions de développement
  • Il peut modifier du code au-delà de ce qui est demandé
  • Il peut considérer une tâche terminée sans l’avoir correctement vérifiée

Il nous faut donc des instructions permanentes

Comment doit-il travailler ?



Dans le dépôt, également.

Et pas uniquement dans nos prompts.

3ème problème

L’agent peut se tromper


  • Il peut produire du code qui compile, mais ne fonctionne pas
  • Il peut introduire des régressions
  • Il peut écrire des tests qui ne vérifient pas les bonnes choses
  • Il peut affirmer avoir terminé sans preuve suffisante

Il nous faut donc des tests

Comment savoir si son travail est correct ?



Des vérifications reproductibles et indépendantes.

Et pas uniquement faire confiance à l’agent.

Trois besoins, trois répertoires



docs/   agents/   tests/



  • docs/ : Ce que l’agent doit savoir
  • agents/ : Comment l’agent doit travailler

Documenter une décision


# Décision : sauvegarde en JSON
Contexte : besoin d'un format inspectable.
Choix : JSON versionné avec champ schema_version.
Alternatives : binaire, SQLite.
Conséquence : validation stricte au chargement.

Une décision doit conserver aussi son pourquoi.


Attention


Plus de documentation ≠ meilleur contexte

Un agent doit retrouver rapidement les informations pertinentes.

Mémoire persistante, contexte sélectif


  • Documenter les connaissances durables
  • Référencer plutôt que recopier
  • Charger les documents nécessaires à la tâche
  • Mettre à jour les contrats lorsque le code change
  • Supprimer ou corriger les informations obsolètes

Un piège

Un agent modifie une API, mais les tests passent. Que faire de la documentation ?

A.   Rien : les tests suffisent

B.   La mettre à jour si le contrat a changé

C.   Recopier toute la conversation dans docs/

D.   Supprimer docs/ pour éviter les contradictions

Réponse : B. Une documentation obsolète induira en erreur les futurs agents et les humains.

Ce que l’agent doit recevoir


Une tâche + un contexte ciblé + des contraintes


Et un moyen de vérifier son travail.

Du besoin au travail exécutable

Objectif Décomposition Tâches Vérification


Chaque tâche doit avoir un résultat observable.

Et vérifié

Objectif : sauvegarder une scène

Il nous faut :

  1. Décomposer le travail par responsabilités
  2. Délimiter le périmètre (scope) de chaque tâche
  3. Organiser les dépendances entre les tâches
  4. Définir comment vérifier chaque résultat

Décomposer par responsabilités

Sauvegarde d'une scène
├── Format et validation
├── Écriture des fichiers
├── Lecture des fichiers
├── Interface utilisateur
└── Tests et documentation


Une tâche atomique

Un périmètre explicite

Un résultat attendu

Un critère d’acceptation

« Atomique » ne veut pas dire minuscule :

cela veut dire cohérent et vérifiable.

2. Définir un scope

Chaque tâche doit préciser :

  • Ce que l’agent doit réaliser
  • Les fichiers et modules qu’il peut modifier
  • Les contraintes à respecter
  • Les critères de validation

Une tâche doit être limitée et vérifiable.


Qu’est-ce que l’agent a le droit de modifier ?

Fichiers, modules, interfaces, dépendances, tests, documentation.

Pourquoi limiter le scope ?

  • Réduire les effets de bord
  • Faciliter la revue du diff
  • Rendre les responsabilités visibles
  • Limiter les conflits entre agents
  • Simplifier le retour arrière

3. Organiser les dépendances

A.   Les lancer simultanément sans coordination

Contrat d’entrée et de sortie

  • Entrées : fichiers, formats, interfaces, contraintes
  • Sorties : code, tests, documentation, commit
  • Erreurs : comportements attendus
  • Validation : oracles requis

Quand arrêter l’agent ?

  • Le résultat demandé est atteint
  • Le périmètre serait dépassé
  • Une hypothèse essentielle manque
  • Un test échoue sans diagnostic fiable
  • Une décision architecturale exige arbitrage

4. Prévoir la vérification


Pour chaque tâche, il faut savoir :

  • Quel résultat est attendu ?
  • Comment le tester ?
  • Quels cas d’erreur considérer ?
  • Qui valide le résultat ?


Les critères de réussite doivent être définis avant de déléguer.

Pour cela il nous faut nous appuyer


sur une batterie de tests


Couvrant au maximum l’état voulu du systéme

Niveaux de test

Élément Rôle
Unitaire Vérifier un composant isolé
Intégration Vérifier plusieurs composants ensemble
Système / E2E Vérifier un scénario complet
Régression Détecter les comportements cassés


Composants d’un test

Élément Rôle
Fixture Préparer les conditions initiales
Oracle Déterminer si le résultat est correct

Qu’est-ce qu’un oracle ?

Un moyen de déterminer si un résultat satisfait une propriété attendue.

L’oracle peut être automatique, partiel ou humain.


L’oracle est la clé de la délégation


Il permet de confier l’implémentation à un agent

sans lui confier le jugement de sa propre réussite.


Le reste peut largement être délégué aux agents.

Différentes formes d’oracles


Oracle Ce qu’il vérifie
Compilation Le code respecte les contraintes du compilateur
Valeur attendue Un résultat correspond à une référence
Invariant Une propriété reste vraie
Différentiel Deux implémentations donnent des résultats compatibles
Performance Une mesure respecte un seuil défini
Visuel Un rendu respecte des critères visuels

Compilation ≠ correction


Ça compile !


Et alors ?

Définissons notre oracle


Après une sauvegarde puis un chargement,

on doit retrouver exactement la même scène.



Scène initiale Save Load Scène restaurée


Oracle : les deux scènes doivent être équivalentes.

Implémentons cet oracle


def test_round_trip(tmp_path):
    scene = Scene(objects=[Cube(position=(1, 2, 3))])
    path = tmp_path / "scene.json"

    save(scene, path)
    restored = load(path)

    assert restored == scene


L’oracle est ici la comparaison avec la scène initiale.

Mais cet oracle est-il suffisant ?


Et si save() et load() partageaient la même erreur ?



Les deux fonctions pourraient être compatibles entre elles,

tout en ne respectant pas le format de sauvegarde attendu.

Ajoutons un oracle indépendant


def test_saved_format(tmp_path):
    scene = Scene(objects=[Cube(position=(1, 2, 3))])
    path = tmp_path / "scene.json"

    save(scene, path)
    data = json.loads(path.read_text())

    assert data["objects"][0]["position"] == [1, 2, 3]


On vérifie maintenant une propriété du fichier produit,

indépendamment de load().

Mais même avec deux oracles…


Avons-nous vérifié tous les cas ?

  • Scène vide ?
  • Fichier corrompu ?
  • Version incompatible ?
  • Sauvegarde interrompue ?


Un oracle ne vérifie que ce pour quoi il a été conçu.

Qui vérifie le vérificateur ?



Un oracle peut lui-même être incomplet ou incorrect.



Et si l’agent écrit à la fois le code et les tests,

il peut reproduire la même erreur dans les deux.

Une question délicate

L’agent écrit son code et ses tests. Tous les tests passent.

A.   La fonctionnalité est nécessairement correcte

B.   Il faut confronter les tests aux exigences

C.   Les tests ne servent à rien

D.   La compilation remplace les tests

Réponse : B. Les tests peuvent partager les mêmes erreurs que l’implémentation.

Comment fiabiliser nos oracles ?


  • Définir les propriétés attendues avant l’implémentation
  • Tester les cas limites et les erreurs
  • Utiliser plusieurs vérifications indépendantes
  • Faire relire les critères par un humain ou un autre agent


On peut déléguer l’écriture des oracles,

mais il faut garder le contrôle sur ce qu’ils vérifient.

L’agent annonce : « Terminé ! »



« 12 tests réussis ! »



Est-ce suffisant ?

Une affirmation n’est pas une preuve


L’agent doit fournir des résultats vérifiables :

  • Les tests exécutés
  • Les résultats obtenus
  • Les éventuels échecs
  • Les vérifications non réalisées



Et idéalement, nous devons pouvoir les reproduire.

Mais est-ce que le code est propre ?

Les tests ne suffisent pas


  • Le code respecte-t-il l’architecture du projet ?
  • A-t-il introduit des dépendances inutiles ?
  • Du code dupliqué ou inutile ?
  • Des modifications hors du périmètre prévu ?
  • La documentation est-elle à jour ?


Un code peut être fonctionnel, mais difficile à maintenir.

Git comme système transactionnel


  • Isoler les modifications
  • Examiner les différences (diff)
  • Identifier un état par un commit
  • Revenir en arrière si nécessaire
  • Intégrer uniquement le travail validé



Un commit garantit la traçabilité, pas la correction.

Quand une tâche est-elle terminée ?


  • Le contrat est respecté
  • Les oracles pertinents passent
  • Les régressions sont contrôlées
  • Le code respecte l’architecture
  • La documentation est à jour

Quand paralléliser ?

Quelles tâches sont les plus adaptées à deux agents en parallèle ?

A.   Deux modifications concurrentes du même fichier

B.   Deux modules indépendants avec des interfaces définies

C.   Deux modifications incompatibles de la même API

D.   Deux refontes globales sans coordination

Un problème : le même dépôt


Que se passe-t-il si plusieurs agents

modifient les mêmes fichiers ?

Une solution : Git Worktrees


Chaque agent travaille dans son propre espace.

Projet
├── main/
├── worktree-worker-A/
├── worktree-worker-B/
└── worktree-worker-C/


Des espaces isolés, mais un historique Git partagé.

Branch ≠ Worktree


Branch : une branche de développement

Worktree : un espace de travail indépendant



Une branche permet d’isoler les commits.

Un worktree permet aussi d’isoler les fichiers de travail.



Idéal pour faire travailler plusieurs agents en parallèle.

Mais l’isolation ne suffit pas



Deux agents peuvent modifier indépendamment

des composants qui dépendent l’un de l’autre.



Il faut définir les contrats et les responsabilités

avant de lancer les travaux parallèles.

Une méthode de supervision



Audit Proposition



Lancement Vérification



On sépare l’analyse, la décision,

l’exécution et la validation.

1. Audit


L’agent examine l’état actuel du projet.

  • Explorer le code et les dépendances
  • Identifier les problèmes concrets
  • Justifier les observations
  • Évaluer les conséquences possibles



Aucune modification du code.

2. Proposition


L’agent propose un plan.

  • Les changements envisagés
  • Les modules concernés
  • Les risques et les dépendances
  • Les vérifications nécessaires



L’humain valide le plan avant l’exécution.

3. Lancement


On délègue le travail.

  • Le Lead décompose le chantier
  • Les Workers exécutent leurs tâches
  • Les modifications sont isolées
  • Les tests et la documentation sont mis à jour



Chaque tâche produit un résultat identifiable.

4. Vérification


On examine ce qui a réellement changé.

  • Les oracles passent-ils ?
  • L’architecture est-elle toujours cohérente ?
  • Le code est-il propre ?
  • Y a-t-il des régressions ?
  • La documentation est-elle à jour ?



Alors seulement, on intègre.

Le véritable Power User

C’est celui qui sait organiser,

orienter et vérifier leur travail.
